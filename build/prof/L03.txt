  (pen marks: 5 )
  beat0:
     0: A variable is a named box in memory that holds a value.
     1: Every variable has a name, a type and a value.
  beat1:
     0: The type tells the computer how many bytes to reserve and how to interpret the bits inside.
     1: An int holds whole numbers, a double holds decimals, a char holds one character, a bool holds true or false, and a string holds text.
  beat2:
     0: An int is usually four bytes, thirty two bits, so it holds numbers from about negative two point one billion to positive two point one billion.
  beat3:

     1: That's called overflow, and it's the same two's complement wheel you'll study in digital logic.

[s5] EX  Arithmetic and its gotchas
  • int / int throws away the fraction
  • % gives the remainder — great for clocks, even/odd, digits
  • Never compare doubles with ==
  CODE:
    int a = 7 / 2;        // 3   (integer division drops the .5)
    int b = 7 % 2;        // 1   (remainder, 'modulo')
    double c = 7.0 / 2;   // 3.5
    
    // convert 3725 seconds to h:m:s
    int total = 3725;
    int hours = total / 3600;           // 1
    int minutes = (total % 3600) / 60;  // 2
    int seconds = total % 60;           // 5
    
    // floating point is approximate:
    // 0.1 + 0.2 == 0.30000000000000004
  (pen marks: 10 )
  beat0:
     0: Arithmetic has a few traps.
     1: Seven divided by two, with both numbers as ints, gives three, not three point five.
     2: Integer division throws the fraction away.
     3: The percent sign is the modulo operator, which gives the remainder: seven mod two is one.
     4: These two operators together are incredibly useful.
     5: Here's an example: convert three thousand seven hundred twenty five seconds into hours, minutes and seconds.
     6: Hours: divide by thirty six hundred, giving one.
     7: Minutes: take the remainder after removing the hours, which is one hundred twenty five, and divide by sixty, giving two.
     8: Seconds: the total mod sixty, giving five.
     9: So it's one hour, two minutes, five seconds.
     10: Last trap: decimals are stored in binary, which can't represent point one exactly.
     11: So point one plus point two is actually point three zero zero zero, with a tiny error at the end.
     12: Never compare two doubles with double equals.
     13: Check whether they're close enough instead.

  img: fig:ifflow
  • if (condition) { … } else { … }
  • Comparisons: <  <=  >  >=  ==  !=
  • Combine with && (and), || (or), ! (not)
  • Order matters: check the strictest case first
  (pen marks: 9 )
  beat0:
     0: Programs make decisions with if and else.
     1: If a condition is true, run one block.
     2: Otherwise, run another.
     3: Here's a flowchart for assigning a letter grade.
  beat1:
     0: Conditions use comparison operators: less than, less than or equal, greater than, equal, and not equal.
     1: Careful: a single equals sign assigns a value, and double equals compares.
     2: Mixing them up is one of the most common beginner bugs.
  beat2:
     0: You can combine conditions with and, written as two ampersands, or, written as two vertical bars, and not, written as an exclamation point.
     1: These are exactly the AND, OR and NOT gates you'll build in hardware.
     2: Software logic and hardware logic are the same logic.
  beat3:
     0: And order matters.
     1: We check ninety or above first, then eighty.
     2: If we checked eighty first, a ninety five would get a B.
     3: An else if chain stops at the first true condition.

[s10] V  Functions: build big programs from small, tested pieces
  img: fig:function / fig:stack
  • A function takes inputs (parameters) and returns an output
  • Name it, test it, reuse it
  • Each call gets its own frame on the call stack
  (pen marks: 5 )
  beat0:
     0: As programs grow, we split them into functions.
     1: A function is a named black box: it takes inputs, called parameters, does some work, and returns an output.
     2: Here, CircleArea takes a radius of two and returns about twelve point five seven.
     3: Once it's written and tested, you can call it from anywhere, and you don't have to think about how it works inside.
     4: That's called abstraction, and it's how million line programs stay manageable.
  beat1:
     0: How does the computer keep track of function calls?
     1: With the call stack.
     2: When main calls CircleArea, a new frame is pushed on top, holding CircleArea's own variables.
     3: If that calls Square, another frame goes on top.
     4: When a function returns, its frame is popped off and its variables disappear.
     5: That's why a variable declared inside a function isn't visible outside it.
     6: It's called the variable's scope.
     7: And if a function calls itself forever, the stack overflows, which is where the famous website name comes from.

[s12] V  Pass by value vs. pass by reference
  img: fig:byref
  • By value: the function gets a copy
  • By reference (&): the function gets the original
  • Use & to change the caller’s variable (e.g. swap)
  • const & for big objects you only read
  (pen marks: 7 )
  beat0:
     0: When you pass a variable to a function, C plus plus normally makes a copy.
     1: That's pass by value.
     2: The function can change its copy, and the caller's variable is untouched.
  beat1:
     0: If you add an ampersand to the parameter type, you pass by reference.
     1: Now the parameter is just another name for the caller's variable.
     2: One box, two names.
  beat2:
     0: That's how you write a function that changes its arguments, like a swap function that exchanges two variables.
     1: With pass by value, swap would only swap the copies, and nothing would happen.
  beat3:
     0: And for big objects like long strings or vectors, copying is slow.
     1: So professionals pass them as const reference: no copy, and the const keyword promises the function won't modify it.

[s14] V  Collections: arrays and vectors
  img: fig:array
  • Many values under one name, in a row in memory
  • Index from 0 to size − 1
  • std::vector grows as needed: push_back()
  • Out-of-bounds access = undefined behavior (a top security bug)
  (pen marks: 6 )
  beat0:
     0: Usually you have many values, like the scores of a whole class.
     1: A vector stores them in one row in memory under a single name.
  beat1:
     0: Each element has an index, and indexes start at zero, not one.
     1: So six scores live at indexes zero through five.
  beat2:
     0: A standard vector can grow: call push back to add an item to the end, and size to ask how many there are.
     1: To find the maximum, loop through every element and remember the largest you've seen.
     2: Here, that's ninety nine, at index four.
  beat3:
     0: And here's a serious danger.
     1: Index six doesn't exist, but C plus plus won't stop you from reading it.
     2: You'll get garbage, or a crash, or worse.
     3: Reading or writing past the end of an array, called a buffer overflow, has been behind many of the most serious security vulnerabilities in history.
     4: Use the at function, or check your bounds.

[s15] EX  Putting it together: average and maximum
  CODE:
    double Average(const std::vector<int>& v) {
      int sum = 0;
      for (int x : v) {
        sum += x;
      }
      return static_cast<double>(sum) / v.size();
    }
    
    int Max(const std::vector<int>& v) {
      int best = v.at(0);
      for (int x : v) {
        if (x > best) best = x;
      }
      return best;
    }
  (pen marks: 7 )
  beat0:
     0: Let's combine everything.
     1: The Average function takes the vector by const reference, so nothing is copied.
     2: It loops over every element with a range based for loop, adding to a sum.
     3: Then it divides by the number of elements.
     4: Notice the static cast to double.
     5: Without it, we'd do integer division, and the average of these scores, which is about eighty three point two, would come out as just eighty three.
     6: The Max function starts by assuming the first element is the best, then walks through the rest, replacing best whenever it finds something larger.
     7: These two patterns, accumulate and keep the best so far, show up in almost every program you'll ever write.
     8: One question to always ask: what happens if the vector is empty?
     9: Here, both functions would fail.
     10: Testing edge cases like empty inputs is what separates working code from fragile code.

[s18] V  Debugging and version control
  img: fig:errors / fig:git
  • Read the FIRST compiler error first
  • Print values or use a debugger (gdb) to see what really happens
  • Write small tests for each function
  • git: save snapshots, undo mistakes, collaborate
  (pen marks: 5 )
  beat0:
     0: Every programmer spends a lot of time debugging, so let's talk about bugs.
     1: There are three kinds.
     2: Compile time errors, like a missing semicolon, are the easiest: the compiler tells you exactly where.
     3: Always fix the first error first, because one mistake can cause dozens of follow on messages.
     4: Run time errors crash the program, like dividing by zero or using a bad index.
     5: Logic errors are the hardest: the program runs perfectly and gives the wrong answer.
     6: To find those, print out values at key points, or step through the program line by line in a debugger like g d b, and compare what's happening to what you expected.
     7: And write small tests for each function.
  beat1:
     0: Finally, version control.
     1: Git saves a snapshot of your project every time you commit, with a message describing the change.
     2: If you break something, you can go back.
     3: If you work on a team, everyone's changes can be merged together.
     4: This course uses Git and GitHub for assignments, and every software company in the world uses something like it.
     5: Commit early, and commit often.

[s19] B  Habits of good programmers
  • Plan in plain English (or a flowchart) before coding
  • Meaningful names: total_seconds, not ts
  • Small functions that do one thing

  • Commit often; read error messages carefully

  beat0:

  beat1:
     0: Plan before you type.
     1: Write the steps in plain English or draw a flowchart.
     2: Most bugs are thinking bugs, not typing bugs.
  beat2:
     0: Use meaningful names.
     1: Code is read far more often than it's written, including by you, six months from now.
  beat3:
     0: Keep functions small.
     1: If a function does one thing, it's easy to test, and easy to reuse.
  beat4:
