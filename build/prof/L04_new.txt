[s4] EX  Encapsulation: private data, public methods
  CODE:
    class BankAccount {
     public:
      BankAccount(std::string owner, double opening)
          : owner_(owner), balance_(opening) {}
    
      void Deposit(double amount) {
        if (amount > 0) balance_ += amount;
      }
      bool Withdraw(double amount) {
        if (amount <= 0 || amount > balance_) return false;
        balance_ -= amount;
        return true;
      }
      double Balance() const { return balance_; }
    
     private:
      std::string owner_;
      double balance_;
    };
  (pen marks: 10 )
  beat0:
     0: Here's the class in C plus plus.
     1: The data members, owner and balance, are private.
     2: Code outside the class cannot touch them directly.
     3: The only way in is through the public methods.
     4: Why?
     5: Because the class can now guarantee a rule, called an invariant: the balance never goes negative.
     6: Deposit ignores negative amounts.
     7: Withdraw refuses to take out more than you have, and returns false to say so.
     8: If balance were public, any line in the whole program could set it to minus a million, and the bug could be anywhere.
     9: Notice three more details.
     10: The constructor, the function with the same name as the class, initializes a new object, using a member initializer list after the colon.
     11: The const after Balance promises that method doesn't change the object.
     12: And the underscore at the end of member names is a common style convention so you can tell members from local variables at a glance.

[s5] EX  Using objects, and splitting code into files
  CODE:
    // bank_account.h  — the interface (what)
    class BankAccount { … declarations … };
    
    // bank_account.cc — the implementation (how)
    void BankAccount::Deposit(double amount) { … }
    
    // main.cc
    #include "bank_account.h"
    int main() {
      BankAccount alice("Alice", 100.0);
      alice.Deposit(20.0);

        std::cout << "Insufficient funds\n";
      }
      std::cout << alice.Balance() << "\n";   // 120
    }
  (pen marks: 7 )
  beat0:
     0: Using an object looks like this.
     1: Create alice with an opening balance of one hundred.
     2: Call Deposit with the dot operator, adding twenty.
     3: Try to withdraw five hundred: the method refuses and returns false, so we print insufficient funds.
     4: The balance is still one hundred twenty.
     5: In real projects, each class is split into two files.
     6: The header file, dot h, declares the interface: what the class can do.
     7: The source file, dot c c, defines the implementation: how it does it.
     8: Other code only includes the header.

     11: The double colon is called the scope resolution operator, and it's the same one in s t d colon colon c out.

[s6] V  How memory really works: stack, heap and pointers
  img: fig:stackheap
  • Stack: local variables, freed automatically
  • Heap: objects created with new, live until delete
  • Pointer = a variable holding an address
  • &x → address of x · *p → the thing p points to
  (pen marks: 7 )
  beat0:
     0: Now let's look under the hood, because computer engineers need to know where data lives.
     1: A program's memory has two main areas.
     2: The stack holds local variables.
     3: They're created when a function starts and destroyed automatically when it returns.
  beat1:
     0: The heap is for objects that must outlive the function that created them, or whose size isn't known until run time.
     1: You create them with new, and they stay until someone calls delete.
  beat2:
     0: How do you find something on the heap?
     1: With a pointer: a variable whose value is a memory address.
     2: Here, p lives on the stack and holds the address of a Circle object on the heap.
  beat3:
     0: Two operators: ampersand x gives you the address of x, and star p follows the pointer to the thing it points at.
     1: Pointers are how linked lists, trees, operating systems and device drivers work.
     2: In embedded systems, you'll even use pointers to specific addresses to control hardware registers directly.

     1: Ampersand x means the address of x.

[s9] V  Memory bugs — and the modern fix
  img: fig:membugs
  • Leak: forgot to delete → memory slowly runs out
  • Dangling: used after delete → random crashes
  • RAII: tie a resource’s lifetime to an object
  • std::unique_ptr deletes automatically
  (pen marks: 4 )
  beat0:
     0: Manual memory management causes three classic bugs.
     1: A memory leak: you new an object and never delete it.
     2: Each leak is small, but a server that leaks a little on every request will eventually run out of memory.
  beat1:
     0: A dangling pointer: you delete an object but keep using the pointer.
     1: The memory may already belong to something else, so you get random, hard to reproduce crashes.
     2: Deleting twice is just as bad.
     3: Studies by Microsoft and Google have found that around seventy percent of serious security vulnerabilities in their large C and C plus plus code bases are memory safety bugs like these.
  beat2:
     0: Modern C plus plus fixes this with an idea called RAII: resource acquisition is initialization.
     1: Tie the lifetime of a resource to an object on the stack, and let its destructor clean up automatically.
  beat3:
     0: The standard library's unique pointer does exactly this.
     1: When the unique pointer goes out of scope, it deletes the object for you.
     2: No leaks, no double deletes.
     3: The rule in modern code: avoid raw new and delete, and use smart pointers or standard containers instead.

[s11] V  Inheritance: “is-a” relationships

  • Abstract base: Area() = 0 means “every shape must define this”
  (pen marks: 3 )
  beat0:
     0: The second relationship is inheritance, an is a relationship.
     1: A circle is a shape.
     2: A rectangle is a shape.
  beat1:
     0: In C plus plus, you write class Circle, colon, public Shape.
     1: Circle automatically gets everything Shape has, like its name, and adds its own data, like a radius.
  beat2:
     0: Each derived class can override behavior that differs.
     1: Every shape can report its area, but a circle computes pi r squared, and a rectangle computes width times height.
  beat3:
     0: In the base class, Area is declared virtual and set equal to zero.
     1: That makes it a pure virtual function, and Shape an abstract class.
     2: You can't create a plain Shape, only specific shapes.

[s12] V  Polymorphism: one call, many behaviors
  img: fig:vtable
  • Store different shapes in one container of Shape pointers
  • s->Area() calls the RIGHT version at run time
  • Add a Triangle later — the loop never changes
  (pen marks: 6 )
  beat0:
     0: Now the payoff.
     1: We can keep a single vector of pointers to Shape, holding circles and rectangles mixed together.
  beat1:
     0: When the loop calls Area on each one, C plus plus figures out at run time which version to call, based on the object's real type.
     1: A circle of radius one gives three point one four.
     2: The two by three rectangle gives six.
     3: A circle of radius two gives twelve point five seven.
     4: The total is about twenty one point seven one.
     5: This is called polymorphism, Greek for many forms.
     6: Under the hood, each object carries a hidden pointer to a table of its class's virtual functions, called the v table, and the call looks up the right entry.
  beat2:
     0: Here's why that's powerful.
     1: Next month, someone adds a Triangle class.
     2: The loop that totals the areas doesn't change at all.
     3: Code written today works with types invented tomorrow.
     4: That's how plugin systems, graphics engines and device driver frameworks are built.

[s15] EX  Operator overloading: making your types feel built-in
  CODE:
    class Fraction {
     public:
      Fraction(int n, int d) : num_(n), den_(d) { Reduce(); }
      Fraction operator+(const Fraction& o) const {
        return Fraction(num_ * o.den_ + o.num_ * den_, den_ * o.den_);
      }
     private:
      int num_, den_;
      void Reduce();   // divide both by their GCD
    };
    
    Fraction a(1, 2), b(1, 3);
    Fraction c = a + b;     // (1·3 + 1·2) / (2·3) = 5/6
  (pen marks: 6 )
  beat0:
     0: C plus plus lets you define what operators mean for your own types.
     1: Here's a Fraction class.
     2: We define operator plus, so you can add fractions with a normal plus sign.
     3: To add a over b and c over d, the numerator is a d plus c b, and the denominator is b d.
     4: So one half plus one third is one times three plus one times two, over two times three: five sixths.
     5: The constructor calls Reduce, which divides the top and bottom by their greatest common divisor, so two fourths automatically becomes one half.
     6: That's encapsulation again: every Fraction object is always stored in lowest terms.
     7: The standard library uses operator overloading everywhere: strings use plus to join, streams use the arrows for input and output, and complex numbers, which you'll use in circuits, overload all the arithmetic operators.

     2: Frameworks like Google Test run hundreds of these in seconds.
  beat1:
     0: A test might create an account with one hundred, deposit twenty, and expect the balance to equal one hundred twenty.
  beat2:

     1: Try to withdraw more than the balance, and expect false, with the balance unchanged.

     1: Write a test that fails, which is red.

     4: Tests are what let professional teams change big programs without fear.

[s18] B  Design principles to remember
  • **Encapsulate:** keep data private; expose a small, clear interface
  • **Single responsibility:** one class, one job
  • **Prefer composition** over deep inheritance trees
  • **Program to an interface:** depend on Shape, not Circle
  • **DRY:** don't repeat yourself — factor out shared code
  • **RAII:** let objects clean up after themselves
  (pen marks: 8 )
  beat0:
     0: Let's collect the design principles from today.
  beat1:
     0: Encapsulate.
     1: Keep data private and expose a small, clear interface, so every object can protect its own rules.
  beat2:
     0: Single responsibility.
     1: Each class should have one job.
     2: If you describe a class with the word and, it's probably two classes.
  beat3:
     0: Prefer composition.
     1: Inheritance is powerful, but deep hierarchies become rigid.
     2: Building objects from parts is usually more flexible.
  beat4:
     0: Program to an interface.
     1: Write code that depends on the general Shape, not the specific Circle, so new types plug right in.
  beat5:
     0: Don't repeat yourself.
     1: If you copy and paste code, factor it into a function or a base class instead.
  beat6:
     0: And RAII.
     1: Let objects clean up their own resources: memory, files, locks.
     2: You'll see the same pattern in operating systems, where a lock guard automatically releases a lock.
