[s1] V  Big-O: how does the cost grow?
  img: fig:bigo
  • Count steps as a function of input size n
  • Keep only the fastest-growing term
  • O(log n) ≪ O(n) ≪ O(n log n) ≪ O(n²) ≪ O(2ⁿ)
  • An algorithm choice can mean 1 ms vs 17 minutes
  (pen marks: 8 )
  beat0:
     0: To compare data structures, we need a way to measure speed that doesn't depend on the computer.
     1: So we count steps as a function of the input size, n.
  beat1:
     0: And we only care about how that count grows for large n.
     1: If a loop takes three n plus five steps, we just say it's order n, written big O of n.
     2: Constants and smaller terms don't matter when n is a billion.
  beat2:
     0: Here are the common growth rates, on a log log chart.
     1: Logarithmic barely grows.
     2: Linear grows in step with n.
     3: n log n is a bit worse.
     4: n squared shoots up.
     5: And two to the n is hopeless beyond tiny inputs.
  beat3:
     0: The difference is dramatic.
     1: For a million items, on a computer doing a billion steps per second, a linear algorithm takes about a millisecond, n log n about twenty milliseconds, and n squared about seventeen minutes.
     2: Choosing the right algorithm often matters far more than buying a faster computer.

[s2] V  Arrays vs. linked lists
  img: fig:listarray
  • Array: contiguous → instant access a[i], cache-friendly
  • Inserting in the middle: shift everything → O(n)
  • Linked list: insert/remove anywhere in O(1) (given the node)
  • But reaching element i means walking → O(n)
  (pen marks: 6 )
  beat0:
     0: The two most basic ways to store a sequence.
     1: An array, or vector, keeps elements side by side in one block of memory.
     2: To get element i, the computer just computes the address, start plus i times the element size.
     3: That's instant, order one.
     4: Arrays are also cache friendly, because the processor loads neighboring elements together, which makes them very fast in practice.
  beat1:
     0: But inserting at the front means shifting every other element over by one: order n.
  beat2:
     0: A linked list stores each element in its own node, scattered in memory, with a pointer to the next node.
     1: To insert, you just rewire two pointers.
     2: Order one.
  beat3:
     0: But to reach element i, you have to start at the head and follow i pointers.
     1: Order n.
     2: Every data structure is a set of tradeoffs like this.
     3: The skill is knowing which operations your program does most.

[s4] V  Stacks: last in, first out
  img: a:plates / fig:stack1 / fig:stack2 / fig:stack3
  • push onto the top, pop from the top
  • Undo history, browser Back button
  • The call stack for function calls
  • Checking balanced brackets: ( [ { } ] )
  (pen marks: 3 )
  beat0:
     0: A stack is like a stack of plates.
     1: You add to the top and take from the top.
     2: Last in, first out.
  beat1:
     0: Undo is a stack.
     1: Every action you take is pushed: you type hello, then make it bold.
  beat2:
     0: Then you delete a line.
     1: That's pushed on top.
  beat3:
     0: Press control Z, and the most recent action is popped off and undone first.
     1: The browser's back button works the same way.
     2: And the call stack you met in programming is literally a stack of function frames.
     3: Compilers also use stacks to check that brackets are balanced: push every opening bracket, and every closing bracket must match the one on top.

[s6] V  Queues: first in, first out
  img: fig:queue
  • enqueue at the back, dequeue from the front
  • Print jobs, network packets, task scheduling
  • Circular buffer: fixed array that wraps around
  • Used in every UART and keyboard driver
  (pen marks: 4 )
  beat0:
     0: A queue is a line at a store: first in, first out.
     1: New items join at the back, and items leave from the front.
  beat1:
     0: Print jobs wait in a queue.
     1: Network routers queue packets.
     2: Operating systems queue processes that are ready to run.
  beat2:
     0: A neat way to build one is a circular buffer: a fixed size array where the head and tail indexes wrap around to the start when they reach the end, using the modulo operator from discrete math.
  beat3:
     0: This matters a lot in embedded systems.
     1: When bytes arrive on a serial port faster than your program can handle them, an interrupt routine drops them into a circular buffer, and the main program pulls them out later.
     2: You'll write exactly this in the embedded systems course.

[s7] V  Recursion: functions that call themselves
  img: fig:fib
  • Base case + a smaller version of the same problem
  • factorial(n) = n × factorial(n − 1), factorial(0) = 1
  • Naive Fibonacci recomputes subproblems → O(2ⁿ)
  • Memoization (cache answers) → O(n)
  (pen marks: 5 )
  beat0:
     0: A recursive function solves a problem by calling itself on a smaller version of the same problem, until it reaches a base case it can answer directly.
  beat1:
     0: Factorial is the classic: n factorial is n times n minus one factorial, and zero factorial is one.
     1: Recursion is natural for anything that's defined in terms of smaller pieces of itself, like trees, file directories, and the merge sort we'll see shortly.
  beat2:
     0: But be careful.
     1: Fibonacci, where each number is the sum of the two before it, looks perfect for recursion.
     2: Yet the naive version recomputes the same values over and over.
     3: Look at the tree: fib of three, in red, gets computed again and again.
     4: The total work grows exponentially.
     5: Fibonacci of fifty would take hours.
  beat3:
     0: The fix is memoization: store each answer the first time you compute it, and look it up afterwards.
     1: Now each value is computed once, and the time drops to linear.
     2: That idea, solving subproblems once and reusing them, is called dynamic programming.

     3: Thirty seven is smaller, so it must be in the left half.
     4: Throw away the right half entirely.
  beat1:

[s11] V  Sorting: from O(n²) to O(n log n)
  img: fig:merge
  • Insertion sort: simple, O(n²) — fine for small n
  • Merge sort: split in half, sort each, merge
  • log n levels × n work each = O(n log n)
  • Quicksort / std::sort: O(n log n) in practice
  (pen marks: 4 )
  beat0:
     0: Sorting is one of the most studied problems in computing.
     1: The simple approach, insertion sort, takes each item and slides it into place among the ones already sorted.
     2: It's easy and fine for small lists, but it's order n squared.
  beat1:
     0: Merge sort uses divide and conquer.
     1: Split the list in half, sort each half recursively, then merge the two sorted halves by repeatedly taking the smaller front element.
     2: Look at the picture: we split down to single elements, then merge back up.
  beat2:
     0: There are log n levels of splitting, and each level does order n work merging.
     1: So the total is n log n.
     2: For a million items, that's the difference between about twenty million steps and a trillion.
  beat3:
     0: In practice, you'll usually call the library's sort, like s t d sort in C plus plus, which uses a carefully tuned hybrid of quicksort and other methods, and runs in n log n time.
     1: But knowing why it's fast helps you recognize when your own code accidentally isn't.

[s12] V  Hash tables: look things up in O(1)
  img: fig:hash
  • Hash function turns a key into a bucket number
  • Lookup, insert, delete: O(1) on average
  • Collisions: two keys, same bucket → chain them
  • Python dicts, std::unordered_map, caches, databases
  (pen marks: 6 )
  beat0:
     0: What if you want to find things by name, not by position?
     1: A hash table runs each key through a hash function that scrambles it into a number, then takes that number mod the table size to pick a bucket.
     2: Store the item in that bucket.
  beat1:
     0: To look it up later, hash the key again and go straight to the same bucket.
     1: No searching.
     2: On average, lookup, insert and delete are all order one, no matter how big the table is.
  beat2:
     0: By the pigeonhole principle, some keys must collide in the same bucket.
     1: Here, alice and carol both land in bucket three.
     2: The usual fix is chaining: each bucket holds a short list.
     3: As long as the table isn't too full, those lists stay tiny.
  beat3:
     0: Hash tables are everywhere: Python dictionaries, C plus plus unordered maps, web caches, compilers' symbol tables, and the indexes inside databases.
     1: If you only remember one data structure from this course, make it this one.

[s14] V  Binary search trees
  img: fig:bst
  • Left subtree smaller, right subtree larger
  • Search, insert, delete: O(height)
  • Balanced → height ≈ log₂ n
  • std::map, databases (B-trees), file systems
  (pen marks: 5 )
  beat0:
     0: A binary search tree keeps data sorted while still allowing fast inserts.
     1: Each node has up to two children.
     2: Everything in the left subtree is smaller, and everything in the right subtree is larger.
  beat1:
     0: To find forty, start at the root, fifty.
     1: Forty is smaller, go left to thirty.
     2: Forty is bigger, go right.
     3: Found it.
     4: The cost is the height of the tree.
  beat2:
     0: If the tree stays balanced, the height is about log base two of n, so a million items need only about twenty comparisons.
     1: But insert items in sorted order into a plain BST and it degenerates into a long chain, as slow as a linked list.
     2: Self balancing trees, like red black trees, rotate nodes to stay balanced automatically.
  beat3:
     0: The C plus plus s t d map is a red black tree.
     1: Databases and file systems use a wide, shallow cousin called a B tree, designed so that each node fills one disk block.
     2: You'll see B trees in the databases course.

[s16] V  Heaps and priority queues
  img: fig:heap
  • Always know the smallest (or largest) item
  • Insert and remove-min: O(log n)
  • Stored compactly in an array
  • OS schedulers, Dijkstra, event simulations
  (pen marks: 5 )
  beat0:
     0: Sometimes you don't need everything sorted.
     1: You just need to repeatedly grab the most urgent item.
     2: That's a priority queue, usually built as a heap.
  beat1:
     0: In a min heap, every parent is smaller than its children, so the smallest item is always at the top.
     1: Inserting or removing the top takes order log n, by swapping an item up or down one level at a time.
  beat2:
     0: A heap is stored compactly in a plain array, with no pointers at all.
     1: The children of position i live at two i plus one and two i plus two.
  beat3:
     0: Operating systems use priority queues to decide which task runs next.
     1: Network routers use them to prioritize traffic.
     2: And the shortest path algorithm on the next slide uses one to always explore the closest location first.

[s17] V  Graphs and shortest paths
  img: fig:dijkstra
  • Store as adjacency lists (sparse) or a matrix (dense)
  • BFS explores level by level (queue)
  • DFS goes deep first (stack / recursion)
  • Dijkstra: shortest weighted paths — how map apps route you
  (pen marks: 6 )
  beat0:
     0: A graph is a set of nodes connected by edges, like the road map from discrete math.
     1: In code, we usually store it as adjacency lists: for each node, a list of its neighbors.
     2: For dense graphs, an adjacency matrix works too.
  beat1:
     0: Breadth first search explores a graph level by level using a queue: all neighbors first, then their neighbors.
     1: On an unweighted graph, it finds shortest paths in number of hops.
  beat2:
     0: Depth first search dives as deep as possible before backing up, using a stack or recursion.
     1: It's how you'd solve a maze, detect cycles, or order tasks that depend on each other.
  beat3:
     0: For weighted graphs, Dijkstra's algorithm finds shortest paths.
     1: Using a priority queue, it repeatedly settles the closest unsettled node and updates its neighbors' distances.
     2: Here, from A, the shortest path to F costs thirteen, going A, C, B, D, E, F, which is not the most direct looking route.
     3: Your phone's navigation app runs refined versions of this on a graph with millions of road segments.

[s18] V  Choosing the right structure
  img: fig:choose
  (pen marks: 7 )
  beat0:
     0: Here's the summary table to keep.
     1: Need fast access by position?
     2: An array or vector.
     3: Undo, recursion or parsing?
     4: A stack.
     5: First come, first served?
     6: A queue.
     7: Look things up by a key?
     8: A hash table, with order one average time.
     9: Need things kept in sorted order with fast search?
     10: A balanced binary search tree, like s t d map.
     11: Always need the smallest or largest item next?
     12: A heap.
     13: Modeling connections, networks or routes?
     14: A graph, with breadth first search or Dijkstra.
     15: The standard libraries of every major language provide all of these, so in practice your job is mostly choosing well, and understanding the costs well enough to avoid accidentally writing an n squared program.
